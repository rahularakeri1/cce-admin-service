ARCHITECTURE SUMMARY (must be understood before reading sub-tasks)
================================================================================

  - SHARED DATABASE: all tables live in `ccedb`'s `public` schema — the SAME
    database/schema every other CCE service already uses. There is NO separate
    `admin_service` database, despite that being what the PRD's own diagram and
    gateway-service's repo docs describe — confirmed against the real dev
    instance. This service's own Flyway ledger is `flyway_schema_history_admin`.
  - SIX tables owned by this service: users, roles, menus, role_menus,
    user_roles, admin_audit_log (all UUID PKs). A SEVENTH table, `api_permissions`,
    already exists in the same schema, owned by gateway-service — this service
    reads and writes ROWS into it but never creates or alters its DDL. Its `id`
    is BIGSERIAL/Long, not UUID — the one deliberate exception.
  - TWO INDEPENDENT AXES: Role->Menu (soft control, cosmetic if wrong) and
    Role->Permission (hard control, gateway-enforced) are configured and saved
    completely independently. Never derive one from the other.
  - ONE IDENTIFIER, THREE SYSTEMS: roles.name = Keycloak realm role name =
    api_permissions.permission_name. Immutable after creation.
  - FULL-REPLACEMENT SEMANTICS on every "set" endpoint (user roles, role menus,
    role permissions) — the payload is always the complete desired set; the
    backend diffs against current state to compute what actually changed in
    Keycloak, but the local DB write replaces the full set.
  - DEFENSE IN DEPTH: this service re-validates every JWT independently of
    gateway-service's own check (signature, iss, aud, exp) and additionally
    resolves the JWT's `email` claim to a local user, rejecting if missing or
    not ACTIVE. (Changed from the PRD's `sub`/`keycloak_id` join — see
    data-dictionary.md §1.1 for the trade-off this accepts.)
  - TWO DIFFERENT PARTIAL-FAILURE STRATEGIES, per flow, not one universal
    rule (see flow-diagrams.md and architecture-overview.md §7):
      - User creation (Flow 2) is LOCAL-FIRST WITH ROLLBACK: local insert
        happens inside an open transaction before either Keycloak call; a
        Keycloak failure, or a commit failure after both Keycloak calls
        already succeeded, rolls the transaction back. A Keycloak account-
        creation failure that's ambiguous (timeout, not a definitive
        rejection) carries an ACCEPTED residual risk of a silent,
        untraceable orphan — a deliberate trade-off, not a bug. Once
        Keycloak's account creation is CONFIRMED (role assignment fails
        afterward, or the commit itself fails), that's always traceable: a
        USER_PROVISIONING_FAILED audit row is written in its own,
        separately-committed transaction (entity_id = the Keycloak
        account's own id) BEFORE the rollback — this needs explicit code at
        BOTH of those failure points, it does not happen automatically.
      - Role -> permission sync (Flow 4) is the OPPOSITE: the local DB
        write commits first and is KEPT regardless of whether the gateway
        sync succeeds — never rolled back, just flagged via a manual
        Re-sync action.
    Nothing is retried automatically in either flow. The invite email (see
    below) never fires unless Flow 2's commit actually succeeds.
  - AUTOMATIC INVITE EMAIL: POST /users triggers a combined VERIFY_EMAIL +
    UPDATE_PASSWORD Keycloak action email (72h link) as the LAST step of
    creation, after USER_CREATED is audited — not a separate admin action.
    POST /users/:id/reset-password reuses the same mechanism as a manual
    resend/reset. A failed send is non-fatal (still 201, with a `warnings`
    entry) — never retried automatically.
  - AUDIT_LOG IS APPEND-ONLY: every mutating endpoint writes exactly one row,
    written through a single AuditLogWriter — no service class inserts into
    admin_audit_log directly.
  - NO HARD DELETE of users this release — deactivation (INACTIVE) is terminal
    and keeps user_roles rows for re-activation.

SUB-TASK A9: Users — List & Create (Keycloak Provisioning)
================================================================================

DESCRIPTION:
  First endpoint that talks to Keycloak. Implements B-30, B-31, B-32 and the
  flow in flow-diagrams.md "Flow 2 — User creation" exactly, including the
  partial-failure path.

DELIVERABLES:
  1. client/KeycloakGateway.java (interface) + its real implementation
     wrapping keycloak-admin-client — createUser, assignRealmRoles,
     executeActionsEmail(userId, ["VERIFY_EMAIL","UPDATE_PASSWORD"], lifespan).
     Wrapped behind an interface specifically so service-layer tests can
     mock it without a running Keycloak (milestone B3 note)
  2. controller/UserController.java + service layer — LOCAL-FIRST ordering
     (changed from an earlier Keycloak-first draft — see flow-diagrams.md
     Flow 2 for the full reasoning):
     - GET /admin/v1/users — filters status/roleId/facilityScope/q,
       paginated (B-30)
     - POST /admin/v1/users — validate -> check email uniqueness -> BEGIN
       transaction -> insert users + user_roles rows -> insert
       USER_CREATED audit row (both uncommitted) -> create Keycloak user ->
       assign realm roles -> COMMIT -> trigger combined
       VERIFY_EMAIL+UPDATE_PASSWORD action email (lifespan = 72h, matching
       the onboard-insights-user.sh precedent elsewhere in this platform)
       -> 201 (B-31). The transaction stays open across BOTH Keycloak calls
       — a @Transactional method boundary (or equivalent), not two separate
       commits
     - If EITHER Keycloak call fails: ROLL BACK the transaction (local row
       + audit row both vanish) -> 502 KEYCLOAK_SYNC_FAILED. If the account-
       creation call's failure was ambiguous (a timeout, not a definitive
       rejection), Keycloak may have actually succeeded anyway — this is an
       ACCEPTED residual risk of this ordering (a silent, untraceable orphan
       in that rare case), not something this milestone needs to detect
     - If role assignment fails SPECIFICALLY, or the final COMMIT itself
       fails AFTER both Keycloak calls already succeeded: Keycloak's
       account creation is confirmed (not ambiguous) in both these cases,
       so BOTH need the SAME explicit handling — write a
       USER_PROVISIONING_FAILED row in its own, separately-committed
       transaction (entity_type='USER', entity_id = the Keycloak account's
       own id, after = {keycloakId, username, email, reason}) BEFORE
       rolling back the main transaction -> 502 KEYCLOAK_SYNC_FAILED. This
       does NOT happen automatically — the commit boundary itself must be
       wrapped in a catch block that fires this same reconciliation-write
       path, not just the two Keycloak calls
     - The email step only runs after a successful COMMIT. If the email
       send itself fails: do NOT fail the request. Still 201, with a
       `warnings` array entry, and the same USER_CREATED audit row's
       `after` JSON gets `"inviteEmailSent": false`. No retry.
  3. Service-layer tests with KeycloakGateway mocked:
     - happy path -> 201, USER_CREATED audit row present, executeActionsEmail
       called exactly once with both required actions
     - email already exists -> 409 EMAIL_IN_USE, NO transaction opened, NO
       Keycloak call made (verify the mock was never invoked)
     - Keycloak account creation forced to fail -> 502, transaction rolled
       back, NO admin_audit_log row of any kind persists (nothing to
       reconcile for this specific failure point)
     - Keycloak account succeeds, role assignment forced to fail -> 502,
       USER_PROVISIONING_FAILED audit row present with entity_id = the
       Keycloak account id, main transaction rolled back (no users row)
     - Keycloak + both calls succeed, COMMIT itself forced to fail (e.g.
       simulate a connection drop at commit time) -> 502,
       USER_PROVISIONING_FAILED audit row present — same as the
       role-assignment-failure case, proving the commit boundary is
       explicitly guarded too, not just the Keycloak calls
     - Keycloak + DB succeed, executeActionsEmail forced to fail -> still
       201, response has a `warnings` entry, USER_CREATED audit row's after
       JSON has inviteEmailSent=false

ACCEPTANCE CRITERIA:
  - Scenario S2 from the PRD (admin onboards a new user with roles) passes
    against the real local Keycloak, including receiving the real
    combined-action email
  - Validation and uniqueness checks happen BEFORE any transaction is
    opened or any Keycloak call made (test asserts zero Keycloak calls on a
    409)
  - A forced Keycloak account-creation failure rolls back cleanly with NO
    audit row written at all
  - A forced role-assignment failure AND a forced commit-after-success
    failure BOTH produce exactly one USER_PROVISIONING_FAILED audit row
    containing the Keycloak account id, and trigger no email — these are
    two distinct code paths that must both be covered, not one
  - A forced email-send failure after a fully successful creation still
    returns 201, not 502

  3. PUT /admin/v1/users/:id/roles — full desired set in the payload; diff

  5. Extend KeycloakGateway: assignRealmRoles/removeRealmRoles (plural,

  6. Tests: role diff with 5 existing roles + 1 added = exactly one
     Keycloak assign call, zero remove calls (verifies "touch only the
     changed ones", not a full re-sync)

ACCEPTANCE CRITERIA:

  - Deactivating then reactivating a user restores access without

SUB-TASK A13: Role -> Permissions Assignment & Gateway Sync
================================================================================

DESCRIPTION:
  B-42, B-43. The highest-risk endpoint in the service — it is the only one
  that writes to api_permissions (a table owned by gateway-service) and the
  only one that calls out to gateway-service itself. Implements
  flow-diagrams.md "Flow 4" and "Flow 5" exactly.

DELIVERABLES:
  1. client/GatewaySyncClient.java (interface + implementation) — wraps
     POST {gateway-url}/api/permissions/sync-to-keycloak. Interface-wrapped
     so it can be mocked/no-op'd in tests and local dev without a running
     gateway-service (PRD §10 local setup note)
  2. GET /admin/v1/roles/:id/permissions — current permission rows for the
     role (reading FROM the existing api_permissions table, filtered by
     permission_name = role.name)
  3. PUT /admin/v1/roles/:id/permissions:
     - replace api_permissions rows where permission_name = role.name, in
       ONE DB transaction (insert/update/delete rows as needed to match the
       submitted set exactly)
     - commit the transaction
     - THEN call GatewaySyncClient — if it fails, return 502
       KEYCLOAK_SYNC_FAILED but KEEP the already-committed DB change (do not
       roll back)
     - audit ROLE_PERMISSIONS_UPDATED regardless of sync outcome (the DB
       state did change)
  4. POST /admin/v1/roles/:id/sync — re-runs GatewaySyncClient without
     touching any row (the manual "Re-sync" action, scenario S6)

ACCEPTANCE CRITERIA:
  - A simulated gateway-sync failure (mock throws) still leaves the DB
    change committed — verify by reading api_permissions rows back after the
    502 response
  - Scenario S6 (gateway sync fails after a permission save; re-sync
    succeeds) passes end to end
  - PRD milestone B4 exit check: permissions saved, sync client called,
    simulated failure returns 502
  - A role's realm role must exist (confirmed synced) before it can be
    assigned to a user — add an explicit check or document why this is
    enforced procedurally rather than in code (open question, resolve here)
